# SimpleTools 全站优化、首页左右分类布局与缺陷修复计划

日期：2026-11-09  
范围：Web 主应用，并回归 Chrome / VS Code 扩展构建  
目标：优化现有代码与资源管理，将首页分类改为“左侧分类导航、右侧工具内容”，修复本次审查确认的缺陷，最终所有测试通过率为 100%。

## 1. 现状与基线

### 1.1 技术结构

- 技术栈：Vue 3、TypeScript、Vite 8、Tailwind CSS 4、Pinia、Vue Router、Vue I18n。
- 当前有约 866 个受 Git 跟踪的 `src` TypeScript/Vue 文件、171 个工具页面、11 个分类、8 种界面语言。
- 工具元数据集中在 `src/registry/index.ts` 与 `src/registry/tools/`；工具组件已经按 slug 懒加载，不在本次改造中改成首屏全量加载。
- 分类与搜索入口位于 `src/pages/HomePage.vue`；工具卡片由 `src/components/shared/ToolCard.vue` 渲染。
- 收藏和最近使用由 `src/stores/user.ts` 管理，分别使用 `st_favorites`、`st_recent`；存储内容为 slug，最近记录最多保存 20 条，首页目前展示前 6 条。
- 打开 `/tools/:slug` 后，路由在 `src/router/index.ts` 的 `afterEach` 中写入最近使用记录。
- 测试使用 Vitest；默认 Node 环境，组件测试通过 `@vitest-environment jsdom` 和 `@vue/test-utils` 运行。

## 2. 需求边界与默认行为

1. 首页顶部的产品名、标语、搜索框及其位置保持不变；只把顶部分类按钮迁移到新分类导航。
2. 桌面端采用左右结构：左侧为分类侧边栏，右侧为工具内容区。
3. 右侧保留现有能力：默认“全部”视图展示收藏（如有）、最近使用（如有，最多 6 条）和全部工具；选择具体分类后展示该分类工具；搜索时展示匹配结果。
4. 保留当前搜索语义：在“全部”中搜索全站，在具体分类中搜索该分类；搜索和分类可以组合。搜索或选择具体分类时，不展示收藏、最近使用等默认浏览区块。
5. 保留现有收藏、清空最近使用、卡片跳转、工具 slug、路由、本地存储 key 和数据结构，不做数据迁移。
6. 移动端不强行挤压成两列：正文保持单列，分类导航放在工具列表上方并使用可折叠/可滚动导航；`md` 及以上使用固定左侧栏。顶部搜索保持不变。
7. 不引入新 UI、状态管理或测试依赖；不做无关依赖升级、全仓库格式化或大规模重写。
8. “测试通过率 100%”指所有应运行的测试均通过，不等同于要求 100% 代码覆盖率；不得通过 `skip`、`only`、删除测试、放宽断言或忽略错误实现目标。

## 4. 实施步骤

### 阶段 A：补回归护栏并复现问题

1. 新增 `src/pages/HomePage.test.ts`，使用 jsdom、Pinia、内存路由和真实中英文消息挂载首页。
2. 为 B1 写出分类、搜索后标题和计数必须对应 `filtered` 的测试。
3. 为 B2/B3 使用可控 Promise 模拟异步渲染，按“后发起先完成、先发起后完成”的顺序复现旧任务覆盖问题。
4. 为 B4/B5  stub `URL.createObjectURL` / `URL.revokeObjectURL`，复现替换、重载、卸载时未回收的问题。
5. 先确认新增缺陷测试能在旧实现上失败，再修实现；不得只写验证正常路径的测试。

### 阶段 B：首页左右分类布局

主要修改 `src/pages/HomePage.vue`，必要时仅在复杂度确实上升时抽取首页专用小组件，不做无关组件拆分。

1. 保留顶部 hero 和搜索框，移除原顶部分类 chips。
2. 在 hero 下增加响应式容器：
   - `md+`：`aside` 在左，工具内容在右；侧栏宽约 12–14rem，右侧使用 `min-w-0` 防止长名称撑破布局。
   - 侧栏在桌面端可使用 `sticky`，顶部偏移需包含固定头部高度；分类超高时仅侧栏内部滚动，不造成页面横向滚动。
   - `<md`：正文单列，分类导航位于列表上方；所有分类仍可到达，触控目标至少 44px。
3. 左侧导航按 `CATEGORIES` 原顺序渲染“全部”和 `usedCategories`，继续隐藏没有工具的分类；每项显示本地化名称和该分类工具数。
4. 当前项使用明确的选中样式及 `aria-current` 或等效语义；导航具备本地化可访问名称。若新增 `app.categoryNavigation` 等公共文案，必须同步 8 个 locale，不能只加中英文。
5. 分类计数通过一次遍历建立 `Map<CategoryId, number>`，避免模板中为每项反复全量过滤；复用注册表作为唯一数据源，不复制工具清单。
6. 右侧内容规则：
   - 默认全部浏览：保留收藏区、最近使用区和全部工具区。
   - 最近使用保持当前排序、最多 6 条、无效 slug 过滤和“清空”能力。
   - 具体分类：主标题显示当前分类，列表只包含该分类。
   - 搜索：继续使用 `searchTools` 的 slug、keywords、本地化名称/描述和多词 AND 语义。
   - 空结果显示现有 `app.noResults`，不显示空网格。
7. 将主标题改为由 `category`、`query` 和 `filtered.length` 派生，修复 B1；不再硬编码“全部 · 全站总数”。
8. 保持 `ToolCard`、路由和卡片网格的基本视觉样式；按右侧实际宽度检查 1/2/3 列断点，避免侧栏出现后卡片过窄。
9. 不增加分类 URL 参数或额外持久化，除非后续另行提出需求。

### 阶段 C：修复异步渲染竞态与资源泄漏

#### C1. `PdfPageCanvas`（B2）

1. 将每次渲染视为一个带序号的任务，在 `getPage`、页面渲染、`toBlob` 等每个异步边界后检查任务是否仍为最新。
2. 只有最新任务可以更新 `src`、`scale`、`size`；旧任务若已创建对象 URL，必须立即 revoke，不能先替换新图。
3. 卸载时使当前任务失效并回收已保存 URL；卸载后不得再提交状态或遗留新 URL。
4. 处理渲染失败和 `toBlob` 返回空值的路径，避免未处理 Promise 拒绝；不得让旧任务错误覆盖最新任务状态。
5. 保持现有 props、slot、事件和坐标换算契约不变，所有使用 `PdfPageCanvas` 的工具共同受益。

#### C2. `pdfium-preview`（B3）

1. 拆分“执行渲染”和“管理 busy/error”的职责，避免 `openWithPassword` 与 `renderCurrent` 嵌套修改同一 busy 标志；外层任务完成前 busy 不得提前变回 false。
2. 渲染时捕获当前文档、页码和参数的局部快照，通过 generation/token 保证只有最新任务可提交预览、文本、尺寸和错误。
3. 缩略图加载同样绑定文档任务；重载或卸载后停止向当前列表追加旧结果，并回收旧任务已产生但未采用的 URL。
4. 文件切换、密码重试、快速翻页、参数连续变化和卸载均需覆盖；不改变导出格式和现有页面操作方式。
5. 不通过全局修改 `runBusy` 来掩盖这一处嵌套问题；若后续要改共享 busy 语义，需另做所有调用方审计。

#### C3. 对象 URL 生命周期（B4、B5、T1）

1. `image-to-pdf`：抽出统一的列表清理函数，组件卸载时 revoke 所有仍存在的 URL；单项删除保持立即回收且不重复 revoke。
2. `pdf-editor`：把需要统一回收的编辑图片 URL 改为可枚举、可统一清理的所有权结构；加载新 PDF 和卸载时统一回收。
3. 当前待放置图片在替换、PDF 重载和卸载时回收旧 URL。多个编辑共享同一字节对象时，不因删除其中一个编辑而提前 revoke 其他编辑仍在使用的 URL。
4. 优先在现有工具内完成清晰的所有权管理；没有新的复用场景前，不提前抽象复杂通用库。
5. `useObjectUrl.test.ts` 改为挂载宿主组件并真实触发卸载，验证替换、手动清理和卸载清理，消除当前 Vue 生命周期警告。

### 阶段 D：全站低风险优化与一致性检查

1. 优先优化共享路径：首页派生数据、注册表查询、PDF 渲染生命周期、对象 URL 所有权和异步状态，不对 171 个工具做无差别改写。
2. 保留现有按工具懒加载、`Map` 按 slug 查询、存储清洗和共享 `runBusy` 等已经合理的设计，不做为了“优化”而优化。
3. 检查本次修改后的注释、测试名称和文档，确保不再描述旧分类 chips 或旧异步行为。
4. 检查控制台错误、未处理 Promise、重复事件监听和对象 URL 回收；新发现的缺陷先记录复现步骤和影响，再纳入修复，不凭猜测宣称全仓库无 bug。
5. 对比生产构建的首屏入口和工具 chunk，确认首页改造没有把工具实现打包进首屏；没有证据时不做额外代码分割。
6. 对 PDF.js 测试字体警告，优先补齐真实测试资源参数；对环境警告记录 Node 版本与来源，不通过静默日志提高“通过率”。

## 7. 推荐执行顺序与风险控制

1. 先提交到工作树的是测试护栏和 B1–B5 的小范围修复，再实施布局；也可先布局，但每个缺陷必须保持独立可回退。

3. PDF 异步修复优先于视觉微调，因为竞态涉及多个复用方；每改一个共享组件就跑全量测试。
4. 对象 URL 修复坚持“谁创建、谁回收”，避免多个模块同时 revoke 同一 URL。
5. 不在本次修改路由、存储格式、工具 slug、依赖版本或构建资源策略，降低三端回归风险。
6. 若浏览器或扩展环境不可用，应明确标记未验证项，不得把单元测试全绿表述为三端验收完成。
